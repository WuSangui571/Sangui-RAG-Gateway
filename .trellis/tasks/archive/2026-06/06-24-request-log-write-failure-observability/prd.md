# Request Log Write Failure Observability

## Goal

Make `ApiRequestLogService.record(CreateRequestLogCommand)` persistence failures observable without changing successful or failed gateway responses.

The gateway contract is:

- Request-log persistence failure must not affect `/v1/chat/completions` public responses.
- Persistence failure must not be silent. It must emit a safe, testable observability signal.
- Observability must not leak prompts, message content, chunk content, app API keys, upstream keys, provider raw bodies, output previews, stack traces in responses, or full exception messages that can carry sensitive data.

This task is a backend/gateway/security observability hardening task. It is not a request-log schema redesign.

## Classification

Complex Task.

Reason: the work crosses gateway response behavior, request-log service behavior, safe logging, test contracts, and Trellis spec updates. It does not require a DB migration, frontend change, or public API change.

## Scope

### In Scope

- Review and harden the failure boundary in `ApiRequestLogService.record()`.
- Add a safe, explicit observability signal for request-log insert failure.
- Add focused tests for:
  - service-level insert failure safety and observability;
  - controller-level gateway response unaffected by request-log failure;
  - forbidden sensitive values not appearing in the observable signal.
- Update relevant specs so future work does not treat "caught and forgotten" as acceptable.

### Out of Scope

- No changes to `rag_request_log` schema or migrations.
- No new public `/v1/*` response fields.
- No new Admin API response fields.
- No frontend changes.
- No request-log retry queue, dead-letter table, event bus, async worker, or distributed tracing integration.
- No changes to retrieval, prompt construction, chunk evidence, rate-limit semantics, upstream provider behavior, or output-preview access policy.
- No change to gateway auth or admin auth.

## Root Cause / Current Gap

Current code already catches all exceptions inside `ApiRequestLogService.record()` and logs an ERROR line:

```text
Failed to persist request log for request_id={}, errorType={}
```

That preserves the gateway response contract, but current tests only assert that the mapper was called and no exception escaped. They do not assert:

- the error log is actually emitted;
- the log contains a stable request ID and exception class;
- the log omits sensitive fields and exception message text;
- controller responses remain unaffected when the mocked `record()` call itself fails;
- spec language makes the observability requirement explicit enough for future changes.

## Proposed Approach

Prefer the smallest structural contract that removes ambiguity:

1. Keep `ApiRequestLogService.record()` non-throwing for persistence failures.
2. Make the observable failure signal explicit and testable.
3. Keep the signal safe by logging only:
   - stable event/message name;
   - `request_id`;
   - safe IDs if already available and not sensitive (`app_id`, `api_key_id`, `user_id`);
   - intended request-log `status`;
   - intended `error_code`;
   - exception class simple name.
4. Do not log:
   - exception message;
   - full command `toString()`;
   - prompt/messages;
   - chunk content;
   - `retrieval_evidence` raw JSON if it could carry future unsafe fields;
   - `output_preview`;
   - app API key, key hash, authorization header, upstream key, provider raw body, stack trace.
5. Add tests using the repo's existing Spring `OutputCaptureExtension` pattern where practical.
6. Update `.trellis/spec/backend/logging-guidelines.md` and `.trellis/spec/gateway/resilience.md`; update `.trellis/spec/security/rag-security.md` only if needed to clarify safe failure observability boundaries.

## API / Command / Payload Fields

No public API change.

No Admin API change.

No database field change.

Internal method contract remains:

```java
void ApiRequestLogService.record(CreateRequestLogCommand command)
```

Relevant command fields for safe observability:

| Field | Use in failure observability | Safety |
|---|---|---|
| `requestId` | Required primary correlation key | Safe UUID/string generated by gateway |
| `userId` | Allowed if non-null | Safe numeric ID |
| `appId` | Allowed if non-null | Safe numeric ID |
| `apiKeyId` | Allowed if non-null | Safe numeric ID, not plaintext or hash |
| `status` | Allowed if non-null | Safe enum-like string |
| `errorCode` | Allowed if non-null | Safe stable code |
| `model` | Avoid unless needed; provider/model are usually safe but unnecessary for insert failure | Safe but not required |
| `providerName` | Avoid unless needed; provider/model are usually safe but unnecessary for insert failure | Safe but not required |
| `questionSummary` | Do not log on insert failure | Bounded but user-derived |
| `hitChunkIds` | Do not log on insert failure | Safe IDs, but not needed |
| `retrievalEvidence` | Do not log on insert failure | Metadata-only today, but too broad as a raw JSON log field |
| `outputPreview` | Never log | Sensitive preview content |

Recommended internal log event/message:

```text
request_log.persist_failed request_id={} user_id={} app_id={} api_key_id={} status={} error_code={} error_class={}
```

Exact text may follow local style, but tests must assert the stable safe tokens.

## Validation / Error Matrix

| Scenario | Public response | Observable signal | Forbidden leakage assertion |
|---|---|---|---|
| Non-streaming success, `record()` succeeds | 200 OpenAI-compatible success | Normal request-log row insert | Existing assertions remain |
| Non-streaming success, `record()` throws | 200 OpenAI-compatible success | ERROR log with request_id and exception class | No prompt/messages/API key/provider body/output preview/exception message |
| Non-streaming gateway failure after controller boundary, `record()` throws | Original OpenAI-compatible error status/code | ERROR log with request_id, status=failure, original error_code, exception class | No prompt/messages/API key/provider body/output preview/exception message |
| Streaming pre-start failure, `record()` throws | Original OpenAI-compatible JSON error | ERROR log with request_id, status=failure, error_code, exception class | No raw SSE/prompt/key/provider body |
| Streaming terminal success/cancel/failure, `record()` throws in async path | Stream lifecycle behavior unchanged | ERROR log with request_id, terminal status/error_code, exception class | No raw SSE/prompt/key/provider body |
| `CreateRequestLogCommand` includes `outputPreview` | Public response unchanged | Failure log must not include preview text | Explicit negative assertion |
| Mapper exception message includes sensitive-looking text | Public response unchanged | Failure log includes exception class only | Explicit negative assertion for exception message contents |

## Good / Base / Bad Cases

| Case | Expected result |
|---|---|
| Good | Insert succeeds; normal request-log row is persisted with safe fields and existing tests continue to pass. |
| Good | Insert fails; gateway response is unchanged, and a safe ERROR event records request_id, safe IDs, status/error_code, and exception class. |
| Base | Request reaches controller but fails validation, rate limit, model config, retrieval, embedding, upstream, or streaming lifecycle; if request-log persistence also fails, the original gateway outcome remains authoritative and the persistence failure is separately observable. |
| Bad | `record()` failure disappears with no testable signal, or failure logging prints exception message, command `toString()`, prompt/messages, chunk content, `output_preview`, keys, provider body, raw SSE, storage path, stack trace, or environment values. |
| Bad | Controller wraps request-log failure as `500 internal_error`, changes a successful response to failure, or adds a fake fallback row/status. |

## Acceptance Criteria

- [ ] `ApiRequestLogService.record()` still does not throw when mapper insert fails.
- [ ] Insert failure emits a stable ERROR-level observable signal.
- [ ] Insert failure observability includes request_id and exception class.
- [ ] Insert failure observability may include safe numeric IDs and request-log status/error_code.
- [ ] Insert failure observability does not include prompt/messages, bounded question summary, retrieval evidence JSON, output preview, API key material, Authorization header, provider raw body, exception message, or stack trace in responses.
- [ ] Non-streaming controller success response remains 200 even when `apiRequestLogService.record()` throws.
- [ ] Non-streaming controller failure response preserves the original OpenAI-compatible error status/code even when `apiRequestLogService.record()` throws.
- [ ] Streaming request-log failure does not alter existing streaming terminal-status tests.
- [ ] Specs are updated to state "response unaffected but failure observable" as a hard request-log contract.
- [ ] No DB migration, frontend type, DTO, or public response shape changes are introduced.
