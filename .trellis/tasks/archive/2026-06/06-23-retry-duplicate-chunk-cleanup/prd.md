# Auto Retry Duplicate Chunk Cleanup

## Goal

Ensure automatic worker retry and explicit admin retry for document ingestion cannot mix old chunks/embeddings with the new processing result for the same document.

This task follows the upload rollback cleanup work. Upload now avoids orphan original files when metadata/task creation fails; this task protects the downstream ingestion data generated by worker attempts.

## Classification

Complex Task.

Reason: the change crosses the document status machine, durable processing task status machine, chunk and embedding persistence, retry scheduling, admin retry behavior, failure-injection tests, and the existing rule that parser and embedding provider calls must not run inside long database transactions.

The current code already has `clearChunksAndEmbeddings(documentId)` and uses it for explicit retry of terminal `FAILED` tasks and deletion paths. The automatic retry path goes through `DocumentProcessingTaskService.claimNextEligible(...)`, then `DocumentProcessingWorker.processNext()`, then `DocumentService.processDocument(task)`. In the current implementation, the automatic retry path does not visibly clear old chunks/embeddings at the start of a new attempt.

## Invariant

For a single `document_id`, active `rag_document_chunk` and `rag_document_chunk_embedding` rows must represent at most one processing attempt's output.

More concretely:

- Before a worker attempt creates new chunks, stale rows for that document from prior failed/stale attempts must be removed.
- If an attempt fails after writing some chunks, a later retry must clear those rows before writing the replacement chunks.
- If an attempt fails after writing some embeddings, a later retry must clear existing embeddings and chunks before writing the replacement result.
- Explicit admin retry for terminal `FAILED` tasks must keep its existing behavior: clear stale chunks/embeddings, reset document to `UPLOADED`, reset task to `PENDING`, and set the KB to `PROCESSING`.
- `PENDING` or `RETRYABLE` explicit retry remains idempotent and must not mutate chunks or task state.
- `PROCESSING` explicit retry remains rejected with `409 DOCUMENT_PROCESSING`.
- `SUCCEEDED` + `READY` explicit retry remains rejected; replacement/reprocess of successful documents is a future contract.

## Validation / Error Matrix

| Scenario | Expected behavior | Assertion points |
|---|---|---|

| First worker attempt fails before any chunk is written | Task becomes `RETRYABLE` or `FAILED` based on attempts; document becomes `FAILED`; no embeddings; no stale chunks | `DocumentServiceTest` |

| Terminal `FAILED` explicit retry | Clears chunks/embeddings, resets document to `UPLOADED`, clears `chunk_count` and error, resets task to `PENDING`, sets KB `PROCESSING` | existing plus strengthened `DocumentServiceTest` |

| Missing document explicit retry | Returns `404 NOT_FOUND`; no cleanup or task mutation | existing admin/service error contract |

## Good / Base / Bad Cases

| Case | Expected result |
|---|---|
| Good | A failed automatic attempt can leave partial generated rows, but the next eligible worker attempt clears the document's old embeddings and chunks before writing the new attempt output. After success, only the latest attempt's chunks and embeddings are active. |
| Base | Parser, storage read, or embedding provider failures remain visible through document/task failure state; stored original files are preserved; existing ready documents keep the KB `READY` when applicable. |
| Bad | Automatic retry appends or conflicts with old `document_id + chunk_index` rows, leaves old embeddings attached to old chunk IDs, silently swallows cleanup failure, marks a partially embedded document `READY`, or turns already `READY` documents into implicit replacements. |

## Technical Approach

Preferred approach:

1. Identify a single attempt-start cleanup boundary for worker-driven processing.
2. Ensure that boundary runs before `parseDocumentContent(...)` writes new chunks for an automatic attempt.
3. Keep parser and embedding provider calls outside long-held database transactions.
4. Keep cleanup failure visible. Do not catch and continue to fake success.
5. Keep explicit retry semantics aligned with current admin API matrix.
6. Avoid duplicating cleanup logic; reuse `clearChunksAndEmbeddings(...)` or a small named helper if additional document-state reset is needed.

Implementation should not add hidden fallbacks. If cleanup fails, the attempt should fail visibly and the task should transition according to the retry policy.
